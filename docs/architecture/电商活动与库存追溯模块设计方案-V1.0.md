# 电商活动与库存追溯模块设计方案

版本：1.0  
日期：2026-11-03  
状态：用户已基本确认方案并授权实施基础体验版；设计建议与后续扩展仍按下文区分

## 1. 目标与适用范围

在现有商品、客户、价格规则、客户报价模块上，扩展电商活动、销售订单、库存与出入库管理，形成两个业务闭环：

1. 按平台、店铺、活动和商品，记录可叠加的优惠方案、实际成交优惠和最终价格，支持历史查询与统计。
2. 按物料、生产批次和单件厂家序列号，记录入库、组套、销售发货、寄样、退货等全过程，追踪每件实物的数量、时间、去向及原因。

本文记录本次新增模块的设计，不代表功能已经实现。既有模块沿用现有系统；本次扩展的范围、用户确认事实和设计建议以本文区分记录，后续明确指示优先。原开发规格中“库存不在首期范围”的描述属于旧阶段边界，不应据此否定本次扩展。

## 2. 已确认事实与待定事项

### 2.1 用户已确认

- 每件产品都有厂家序列号。
- 当前只设计自有仓库，不接入平台仓或第三方仓。
- 暂时没有可导出的平台订单数据。
- 组合商品全部是实体套装。
- 每个产品型号对应唯一物料编码，每批进货需要记录生产批号。
- 销售出库需要记录销售单号、渠道、物流费用、发货时间等信息。
- 需要覆盖销售、寄样及其他合理出入库场景。
- 方案整理阶段仅设计；用户随后授权使用 GPT-6 Luna 协作实施，并先在系统内体验再优化。

### 2.2 设计建议，尚不视为用户逐项确认

- 第一期使用一个默认自有仓库，数据结构保留多仓库扩展能力。
- 物料编码全局唯一；厂家序列号按“物料编码＋厂家序列号”唯一校验，防止不同型号的厂家编码重复被误拒绝。
- 序列号使用文本保存，保留前导零、字母和符号；扫描输入只清理首尾空白，不擅自更改大小写。
- 标品和套装逐件追溯；配件是否按数量、批次或序列号管理，由商品追踪方式决定。
- 无套装级厂家序列号时，生成内部套装追溯码并贴码。
- 第一期手工维护销售订单和实际优惠，预留批量导入及平台接口能力。
- 币种沿用人民币；金额使用十进制计算，展示两位小数。

### 2.3 实施前需要确认

1. 历史实物的序列号清单、生产批号是否齐全，缺失如何补录及确认。
2. 厂家序列号是否跨型号全局唯一，是否区分大小写。
3. 套装是否有厂家整套序列号；封装套装能否取得内部组成件序列号，采集时点如何安排。
4. 安全库存、保质期、成本核算和出入库审批是否需要第一期启用。
5. 活动实际需要支持哪些优惠类型及计算顺序，以真实业务样例验证。

## 3. 菜单与页面入口

| 一级位置 | 页面或入口 | 用途 |
|---|---|---|
| 产品资料 | 基础资料补充 | 物料编码、库存管理单位、追踪方式、可选安全库存 |
| 商品详情 | 活动记录、库存、出入库记录页签 | 从商品查看相关业务 |
| 电商活动 | 活动列表、活动详情、优惠方案、活动统计 | 管理计划与实际活动结果 |
| 销售订单 | 订单列表、详情、发货与退货 | 记录成交，连接活动和库存 |
| 库存与出入库 | 库存总览、入库、出库、套装组装、追溯、盘点 | 管理实物流转 |
| 基础资料 | 平台店铺、仓库、业务原因、物流公司 | 维护共用选项 |

销售订单建议独立作为一级入口，活动详情可直接进入相关订单。报价确认不等于销售成交，也不自动扣库存；后续可从已确认报价创建销售订单。

列表统一使用服务端搜索、筛选和分页；商品选择统一采用远程搜索与分批加载，只展示型号和名称。长文本保持固定行高、省略显示，提供完整查看入口；业务明细放详情页。

## 4. 关键概念和关联

| 概念 | 定义与边界 |
|---|---|
| 商品型号 | 商业型号，对应一个内部物料编码 |
| 物料编码 | 稳定的内部库存身份，不使用平台商品 ID 替代 |
| 生产批次 | 厂家生产的一批产品，归属具体物料 |
| 入库单 | 某次实际收货；可包含多个生产批次，一个生产批次也可分多次入库 |
| 单件实物 | 通过厂家序列号追踪的具体产品 |
| 套装实例 | 一套具体实体商品，与内部组成件的实际身份关联 |
| 活动方案 | 某店铺、某时间段内商品可使用的优惠规则 |
| 销售订单 | 实际成交和优惠记录，可分多次发货 |
| 发货单／包裹 | 某次实际发货及物流，不把一个订单限制为一个运单 |
| 库存流水 | 单据过账产生的可追溯变化，包含实物、位置和状态变化 |

核心链路：活动及优惠版本 → 销售订单及实际优惠快照 → 发货出库 → 套装或单件序列号。退货、退款、换货继续关联原订单和原发货记录。

## 5. 电商活动模块

### 5.1 平台、店铺和渠道商品

维护平台名称、店铺名称、编码和启用状态。内部商品可映射多个平台商品 ID、平台 SKU 和商品链接，记录上架状态，库存身份始终使用内部物料编码。

### 5.2 活动与活动商品

活动维护名称、起止时间、平台店铺范围、负责人、规则附件、备注及状态。支持预售、开门红、返场等可选阶段；每个阶段有明确时间范围。

建议状态：草稿、已发布、已结束、已归档。发布后修改规则生成新版本，历史订单继续引用成交时的版本。

活动商品维护活动标价、适用时段、可选数量限制，以及普通用户、会员等多个优惠方案。标准市场零售价可作为测算参考，活动价格独立保存。

### 5.3 优惠规则

| 类型 | 主要参数 |
|---|---|
| 直接立减 | 减免金额 |
| 满额减免 | 门槛、减免金额、是否每满减、封顶 |
| 折扣 | 折扣比例、最高优惠金额 |
| 满件优惠 | 件数门槛、减免或折扣 |
| 会员优惠 | 身份要求及对应优惠方式 |
| 赠品 | 商品、数量、触发条件 |
| 运费优惠 | 包邮条件、运费减免 |

每项优惠需要记录商品级或订单级作用范围、有效时间、门槛计算基数、计算顺序、叠加及互斥关系、优惠承担方和特殊资格。承担方可为商家、平台或共同承担，共同承担时分别记录金额。

跨商品、跨店凑单或特殊资格才能满足的优惠，测算页面明确标注外部条件。测算结果称“预计到手价”，不能自动当作实际成交金额。赠品记录价值和库存消耗，但不能直接视为买家现金减免。

### 5.4 实际优惠与统计

实际订单单独记录真正使用的优惠、金额及承担方。带出活动方案后由操作人确认，不能默认全部优惠均已使用。

订单级优惠需分摊到商品行。建议按符合条件商品的金额比例分摊，并使用稳定规则分配分位尾差，保证行分摊合计等于订单优惠。规则在实施前结合实际平台样例确认。

只知道最终实付、尚不清楚每张券金额时，允许保存“优惠明细待补”。未知优惠不填零，不反推成确定券金额。统计展示明细完整性，避免部分数据冒充全量实际。

示例：商品原金额 399.00 元，店铺券 30.00 元、平台券 20.00 元、会员优惠 10.00 元，买家商品实付 339.00 元。其中商家承担 40.00 元、平台承担 20.00 元。运费、手续费、平台结算、退款分别记录，不能将买家实付直接视为商家结算。

统计维度：活动、阶段、平台、店铺、商品和日期。指标包括下单数量、发货数量、退货数量、净发货数量、商品原金额、优惠金额、买家实付、退款、各类优惠使用次数与金额、商家和平台承担金额、物流费用、明细待补订单数。

“可叠加优惠种类”“实际使用种类”“使用次数”分开统计；成交数量和净发货数量分开展示。

## 6. 销售订单模块

### 6.1 订单录入

系统生成内部销售单号。维护订单时间、渠道、店铺、可后补的外部订单号、客户或接收方、商品明细、数量、活动归属、原金额、实际优惠、买家实付、运费及备注。

非活动销售可不选活动；不同商品行允许有不同活动归属。平台外部订单号在同一店铺内校验重复，支持幂等导入的后续扩展。

第一期以手工录入为主，不承诺自动获取平台销量。商品名称、型号、物料、活动规则和金额等保存成交快照，后续修改基础资料不影响历史记录。

### 6.2 发货、退款与退货

订单确认后可预留库存；发货时选择具体套装或单件序列号。支持部分发货和多包裹；物流公司、运单号、发货时间、实际物流费用、可选签收时间及附件归属发货单或包裹。

订单业务状态、付款退款状态和履约状态分别维护，不用一个状态覆盖所有情况。允许部分退款、部分退货；仅退款不自动增加库存。实物退回后进入待检，验收通过再恢复可销售状态。

售后换货关联原订单、退回序列号、新发序列号和换货原因；历史发货和优惠记录不覆盖。

## 7. 库存与出入库模块

### 7.1 库存总览与数量口径

按物料和仓库展示在库、已预留、待检、冻结、可用及借出未归还数量。可继续展开生产批次和序列号。

可用数量从互斥的实物状态和预留关系计算，避免冻结与预留重复扣减。借出实物不计入仓库可用数量，但保留借用人、用途和预计归还时间。组套中的组成件不能再次作为独立可用库存计算。

库存数量由已过账业务产生，不在商品资料中直接覆盖。盘点差异通过调整单处理。

### 7.2 入库

入库类型：采购或生产入库、销售退货、借样归还、盘盈及期初库存。保留将来调拨入库能力。

入库单头记录单号、类型、来源方、仓库、业务发生时间、经办人、备注、附件；明细记录物料、生产批号、数量、厂家序列号、可选生产日期和有效期、质检状态。

流程：草稿 → 扫码／多行粘贴／导入序列号 → 校验 → 确认入库并过账。序列号管理商品要求数量与有效序列号数量一致，重复实物不可重复入库；销售退货和借样归还复用原实物身份，不另建重复序列号。

### 7.3 出库

| 出库类型 | 特有信息 |
|---|---|
| 销售发货 | 销售订单、收货方、渠道及物流 |
| 寄样赠送 | 接收方、用途、关联客户或项目，不要求归还 |
| 借样借用 | 借用方、用途、预计归还时间、归还状态 |
| 售后换货 | 原订单、原实物、新发实物及原因 |
| 内部领用 | 部门、领用人、用途 |
| 报废、盘亏 | 原因、附件、确认人 |

流程：选择业务原因 → 关联订单或填写用途及接收方 → 选择物料与批次 → 扫描具体序列号 → 完善物流 → 确认出库并过账。

销售出库必须关联销售订单，寄样等其他类型不要求创建虚假销售订单。出库时不得使用待检、冻结、已借出、已出库或已装入其他套装的实物。

### 7.4 单据状态与修正

建议状态为草稿、已确认／待执行、已过账、已取消，具体业务仅启用需要的步骤。业务发生时间与系统操作时间分别保存。

仅实际过账改变库存；预留独立管理。草稿可以删除，已过账单据不可直接修改或删除，通过关联冲销、更正、退货等单据修正。取消订单和预留释放需同步处理。

使用数据库事务、实物锁定或原子条件更新、唯一约束及幂等控制，防止重复点击、并发操作导致同一实物重复发出、重复入库或负库存。

### 7.5 盘点与期初库存

上线前采集物料、生产批次、现有序列号、仓库和状态，先预检再确认期初入库。缺失资料列为异常，不虚构厂家批号或序列号。

盘点记录账面数量、实际数量、差异序列号、原因和确认人。调整通过独立单据形成流水，不直接修改累计余额。

## 8. 实体套装管理

### 8.1 模板与实际组成分离

现有商品组成关系作为套装组成模板；每套实体必须另存实际组成件及序列号。模板改变不重写历史套装组成。

套装具有独立物料编码、套装级厂家序列号或内部追溯码。组成件保留各自厂家序列号、生产批次和历史记录。

### 8.2 两种来源

- 厂家整套交货：套装直接入库，采集可取得的内部组成件身份；组成件不另计独立可用库存。尚未取得的组成信息标为追溯待补，不冒充已完整采集。
- 仓库自行组装：组装单选择实际组成件，消耗组成件独立可用库存，形成套装库存，原子完成状态及关系变更。

销售出库扫描套装码，带出实际组成明细。不能同时再次扣减组成件可用数量。统计套装和组成件时区分“可独立销售库存”与“装配关系”，避免数量及成本重复计算。

### 8.3 拆套与换件

拆套通过单据解除当前装配关系，并记录套装减少、可用组成件恢复及检测状态。换件记录旧件、新件、时间、原因和操作人。组成关系保留有效期间，可还原任意一次发货时套装实际包含哪些实物。

同一组成件不能同时属于两个有效套装；首期不开放嵌套套装，以沿用现有组合嵌套限制。

## 9. 序列号追溯

支持按厂家序列号、内部套装码、型号、物料编码、生产批号、销售单号和运单号查询。

追溯时间线展示：生产批次 → 入库 → 组装／拆套／换件 → 出库 → 接收方与物流 → 退货或归还 → 检测 → 再次入库、出库或报废。

每个节点包含业务单号、发生时间、操作时间、仓库或去向、操作人、原因及附件。实物当前状态必须与流水及有效套装关系一致。

## 10. 数据结构建议

继续采用现有 Vue、NestJS 和 PostgreSQL 单体架构，新增独立实体，避免把业务历史堆入商品备注。

| 数据对象 | 主要关系与作用 |
|---|---|
| 商品扩展 | 物料编码、追踪方式、库存单位、安全库存 |
| 平台、店铺、渠道商品映射 | 内部商品关联外部商品与链接 |
| 活动、阶段、活动商品 | 时间范围、参与店铺和商品 |
| 优惠方案版本、规则及组合关系 | 门槛、顺序、互斥、承担方、发布快照 |
| 销售订单与商品明细 | 成交快照、活动归属、金额和数量 |
| 实际优惠与分摊明细 | 每种优惠及各商品承担金额、完整性 |
| 发货、包裹与实物关联 | 支持拆单发货及多个运单 |
| 退款退货及换货记录 | 关联原订单、原发货和原实物 |
| 仓库、生产批次、单件实物 | 位置、批次、厂家序列号和当前状态 |
| 套装实例与组成历史 | 实际组成件及装配有效期间 |
| 出入库、组装、拆套、盘点单据 | 业务原因、状态、经办人及明细 |
| 库存流水、预留及库存余额 | 可追溯事实、占用关系和查询加速 |

库存余额可作为查询加速结果，库存流水与业务单据构成核对依据；不允许只改余额而缺少来源单据。所有表结构变更通过独立迁移实现，历史数据采用明确的期初导入流程衔接。

## 11. 权限与操作记录

建议拆分活动维护、销售订单维护、库存查看、入库操作、出库操作、组套操作、盘点调整确认、成本查看和统计导出等权限。是否启用逐单审批，在实施前确认。

记录关键操作人、时间、状态变更和修改原因。收货联系人、地址等信息限制在业务所需范围内访问和导出。已引用基础资料通过停用管理，不删除历史关联。

## 12. 实施顺序

以下是实施顺序建议。用户已授权基础体验版开发，细分顺序按依赖调整。

1. 基础资料及库存：物料编码、默认仓库、期初预检导入、批次序列号、入库、出库和追溯。
2. 实体套装：整套入库、组装、实际组成关系，以及基本拆套和换件处理。
3. 销售闭环：手工订单、预留与发货、寄样赠送、借样及归还、基本退款退货。
4. 活动闭环：平台店铺、活动商品、优惠方案、实际优惠录入、分摊和统计。
5. 核对完善：盘点、异常处理、报表导出及完整验收。

首个可用版本应覆盖以上基本闭环。平台自动同步、物流接口、复杂结算及完整成本核算另行规划；后续增加多仓时再启用调拨流程。

## 13. 验收标准

1. 同一型号的物料编码唯一；序列号按最终确认的唯一性规则校验并保留原始文本。
2. 一批生产产品可分多次入库，一次入库可包含多个生产批次，查询关系准确。
3. 重复提交、并发出库不能导致重复库存或同一实物发出两次。
4. 套装组装后组成件不可独立出库；套装出库无重复扣减；可还原发货时的实际组成。
5. 销售订单可部分发货，具体实物与每次发货、运单和物流费用关联。
6. 寄样赠送和借样可区分，借样可查询未归还实物及责任方。
7. 仅退款不增加库存；退回实物待检后才能恢复可用，追溯历史完整。
8. 活动方案准确表达优惠门槛、顺序和互斥；预计到手价与实际成交分开。
9. 实际优惠缺失可标待补；分摊明细合计与订单优惠一致，不虚构券金额。
10. 活动统计分开展示成交、发货、退货、退款及优惠承担方，可定位原始单据。
11. 已过账单据不能直接覆盖或删除，更正保留关联流水。
12. 使用一套真实业务样例，走通入库、组套、活动成交、发货及退货；按型号、订单号和序列号都能查回完整记录。
