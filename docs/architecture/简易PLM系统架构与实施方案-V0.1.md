# 简易 PLM 系统架构与实施方案

版本：V0.1（评估稿）  
日期：2026-11-01  
状态：待确认；未开始开发

## 1. 系统定位与前提

建设公司内部的产品资料和客户报价系统。首期支持不完整的采购基准价，通过人工确认保障对外报价；日常报价逐步沉淀客户贴牌价格。采购基准价与出厂价是同一个人工录入的价格，财务含税成本单独维护。

本方案暂按公司内部人员通过浏览器使用、需要集中管理数据设计。实际用户数、现有服务器、远程访问及现有系统集成情况尚未确认，因此技术选型和部署规模均为建议，不是既定事实。

## 2. 业务模块

| 模块 | 首期职责 |
| --- | --- |
| 登录与权限 | 用户登录，按角色控制资料、成本、规则维护和报价确认权限 |
| 产品与规格 | 产品、配件、组合商品；图片、单位、规格、状态与组成关系 |
| 客户与品牌 | 客户基础资料、客户品牌和多个自有品牌 |
| 基础价格 | 人工维护采购基准价／出厂价、财务含税成本，计算市场零售参考价 |
| 价格规则 | 按产品规格、品牌或客户按需维护价格阶梯及计算方式 |
| 报价计算 | 按规则计算整批／分段价格，计算组合商品参考价，给出缺失提示及明细 |
| 报价单 | 自有品牌、客户贴牌两个页签；报价草稿、逐产品确认、导出和历史查询 |
| 记录与追溯 | 规则变更、单次调价、确认记录、报价版本和计算快照 |

## 3. 业务流程

1. 维护商品、规格和必要的组成关系；采购基准价、财务成本允许缺失。
2. 维护客户与品牌；不为所有客户和产品预建贴牌规则。
3. 建立报价单，选择自有品牌或客户贴牌、商品规格和需要报价的数量。
4. 系统查找适用规则并计算候选价；没有规则时为实际报价的商品按需设置。基准价缺失时，可直接录入价格，不可用缺失基准价计算百分比或折扣。
5. 选择长期保存为客户常用规则，或仅用于本次；首次设置默认前者，允许改为后者。长期规则或本次价格调整留痕。
6. 负责人逐产品确认，各产品全部数量档一起展示；任一档变化后该产品重新确认。全部对外展示商品确认后生成并导出报价。
7. 以后引用客户常用规则时重新计算并逐次确认；历史报价使用当时保存的快照。

## 4. 计价规则

### 4.1 规则配置

每套规则关联适用的商品规格、报价类型以及相应品牌或客户，按数量区间配置价格。支持直接指定单价、百分比加价、折扣等方式；具体百分比／折扣输入习惯、固定金额加减及组合计算仍需确认。区间不得重叠，低于最低区间时不自动报价，提示设置价格或调整规则。

规则可选择：

- **整批计价**：总数量匹配对应区间，全部数量使用该区间单价。
- **分段计价**：各区间对应数量分别乘以各自单价，再汇总金额。

分段计价展示每段数量、单价及金额、总金额；需要展示单价时，另行标明平均单价。平均单价的精度与总额的舍入方式待确认，避免平均单价反乘后产生分差。

采购基准价变化时，直接设置的固定单价保持不变；基于百分比或折扣的价格重新计算并提示复核。缺少基准价时可以直接维护本次价格，经人工确认后报价；也可保存为客户常用固定价格。

### 4.2 组合商品

订购数量乘每套组成项用量，得到组成项计价数量，再按对应价格口径和规则计算。如一套含两个配件，订购 100 套时，配件以 200 个匹配阶梯；如采用分段计价，则先计算 200 个配件总金额，再折算到每套。展示计算明细及价格来源，缺项明确提示，不能将缺失按零处理。允许以人工录入的价格处理缺失并确认报价。

组合商品是否允许嵌套、独立阶梯价格与组成计算结果的优先级，以及不同组成项是否允许采用不同价格口径，仍需业务确认。

## 5. 核心数据关系

以下是概念关系，用于明确业务归属，不代表最终数据库表结构。

| 数据对象 | 主要内容及关系 |
| --- | --- |
| 商品 | 类型、货号、名称、图片、状态；一个商品可有多个规格 |
| 商品规格 | 规格、计价单位及状态；价格和报价以具体规格为对象 |
| 组成关系 | 商品规格与其组成规格、每套用量；禁止循环引用 |
| 客户 | 客户基本资料，可关联客户品牌、客户专属规则和报价单 |
| 品牌 | 自有品牌或客户品牌；自有品牌支持多个 |
| 基础价格 | 商品规格的采购基准价／出厂价、财务含税成本及变更记录 |
| 价格规则 | 商品规格、适用客户或自有品牌、有效范围、整批／分段方式及多个阶梯 |
| 报价单 | 客户、报价类型、品牌、日期、状态与版本 |
| 报价明细 | 商品规格、一个或多个数量档、规则引用、单次调整及计算快照 |
| 确认记录 | 每个产品的确认状态、确认人、时间及当时全部档位；变更后失效 |
| 操作记录 | 价格、规则、报价及确认的关键操作与时间 |

规则匹配必须有明确优先级，避免多条规则同时命中。客户贴牌没有适用规则时提示按需建立，不静默套用通用价；白牌规则的品牌、产品及渠道优先级待确认。报价快照保存当时的商品、数量、价格、规则版本及确认信息，不能只依赖当前规则反算。

## 6. 建议的技术架构

建议采用浏览器访问的内部 Web 系统：

```text
浏览器：产品资料 / 价格规则 / 客户与品牌 / 报价与确认
                         │
                    应用服务
      权限与审计 / 商品资料 / 价格计算 / 报价管理 / 导出
                         │
          关系型数据库 + 产品图片文件存储
```

建议首期使用一个应用和一个关系型数据库，价格计算作为应用内独立业务模块；不预设拆分多个服务。这样便于统一权限、报价事务和历史记录，也能在后续规则增加时集中维护计算逻辑。图片与数据库分别存储，数据库记录图片关联信息。

技术组合建议：前端采用成熟的 Web 界面框架，后端采用团队熟悉的应用框架，数据库采用 PostgreSQL 或同类关系型数据库。具体语言、框架、服务器和导出组件应依据现有技术团队、运维环境、用户规模与格式要求选择，此阶段不锁定。

## 7. 关键设计约束

- **计价口径清晰**：价格规则、数量区间、计价方式、币种、含税口径、单位与生效时间均需明确。金额精度、税率及舍入待确定。
- **缺失不等于零**：缺少价格或规则时显示原因；直接输入价格是独立的人工报价路径。
- **确认基于快照**：某产品任何影响价格的输入或数量档发生变化时，该产品确认失效；对外展示的所有产品确认后方可形成对外报价。价格变化后旧报价的处理以已保存快照为准。
- **历史不可被覆盖**：已确认报价如需更改，复制为新版本并重新确认；保留原报价和变更记录。
- **成本权限**：采购基准价及财务成本按权限查看，对外导出不包含内部成本或计算参数。
- **权限职责**：区分资料、基础价格、长期规则、本次价格调整、报价制作及确认；角色与是否允许自审待确认。
- **可靠性**：数据库与图片纳入备份，并定期验证恢复；备份频率和保留期限随公司要求确定。

## 8. 建议的实施顺序

1. 确认业务规则与报价单模板，整理示例商品、客户、价格和用户角色。
2. 建立产品、规格、组成、客户和品牌管理。
3. 建立基础价格、阶梯规则和可独立验证的计价功能；覆盖整批、分段、组合、缺价及边界数量。
4. 建立自有品牌与贴牌报价、按需建价、本次调整、逐产品确认及历史快照。
5. 完成报价导出、权限、日志、备份恢复及典型业务验收。
6. 导入经业务人员核对的初始数据，选取少量人员试用并修正问题，再决定正式使用。

顺序是功能依赖建议，不代表已授权实施，也不代表工期承诺。开发前根据最终范围和部署条件另行评估工作量。

## 9. 开发前仍需确认

1. 使用人数、是否需要公司外网访问、现有服务器与技术团队情况。
2. 报价单导出格式：是否以现有 Excel 两个页签为模板；PDF 是否也需要。
3. 人民币含税是否为默认口径；是否涉及其他币种、税率、运费；金额及平均单价精度和舍入。
4. 固定加价、折扣与百分比的具体输入方式；是否允许多种方式叠加。
5. 自有品牌线上／线下价格如何配置、市场零售参考价选取方式。
6. 谁能维护价格、调整本次报价和确认报价，制单人与确认人是否可以相同。
7. 客户常用规则与客户品牌、规格之间的适用维度；多条规则匹配的优先级。
8. 组合商品嵌套及独立阶梯价格的优先级；客户数量档和报价单输出的具体表现形式。

这些问题可以在评估阶段继续确认；不应靠未经确认的规则直接实现对外报价。
