# 简易 PLM 技术方案对比与选型

版本：V0.2  
日期：2026-11-01  
状态：技术组合已确认；尚未开始开发

## 1. 评估依据

系统为 10 人以下公司内网应用，前后端同一项目分目录，运行电脑可能为 Windows、Linux 或 macOS，使用现有云端 PostgreSQL，导出 Excel；公司没有专门运维。重点是报价准确、权限和历史可追溯、易部署维护。性能瓶颈预计不是主要选型因素，实际仍需测试。

2026 Stack Overflow 开发者调查的 Web 技术样本共 10,281 人，受访者可多选；React 41.5%、Vue 17.2%、Express 15.6%、Django 11.3%、NestJS 5.8%。Node.js 46.4% 是运行时而不是后端框架，不能直接与框架份额相比。调查反映受访者使用情况，不等同于项目市场份额或中国本地人才分布。来源：https://survey.stackoverflow.co/2026/technology/data/web-framework

## 2. 方案比较

| 方案 | 开发与效果 | 复杂度和维护 | 判断 |
| --- | --- | --- | --- |
| Vue + TypeScript + Express + PostgreSQL | 后台表单、报价规则和 Excel 均可实现；前后端同语言 | Express 起步简单，但权限、校验、模块边界等需要自行组织；项目增长时依赖工程约束 | 合适的轻量选择 |
| Vue + TypeScript + NestJS + PostgreSQL | 业务功能相同，模块、校验和权限结构较明确 | 框架概念和初期代码量更多；前后端同语言；后期功能增长较易分模块 | 推荐，前提是控制依赖与架构规模 |
| Vue + Python Django + PostgreSQL | 内置账号、权限、管理界面有利于基础资料管理；报价仍需定制 | 前后端两种语言与工具；对于复杂自定义报价仍要额外实现 | 可行，维护团队熟悉 Python 时值得选择 |
| React + TypeScript + Node.js + PostgreSQL | 功能可实现；调查中 React 受访使用比例更高 | 前端选型与团队经验、组件生态有关；不能仅凭全球调查断言国内维护成本更低 | 合适替代方案 |

上述难度为结合项目范围的工程判断，不是实测工期。10 人以下的产品管理和报价业务，上述方案均可达到需求；报价准确性由业务规则、数据库事务与测试决定，不由框架名称决定。

## 3. 建议选择

已确认采用 Vue + TypeScript、Node.js + NestJS、PostgreSQL，单项目分 frontend、backend 文件夹，部署一个应用服务。原因：前后端使用统一语言；系统存在价格规则、组合商品、客户差异、人工确认、历史快照和权限等多个业务边界，适度结构化有利于维护；Vue 和 React 都能胜任后台页面，Vue 适合作为表单密集产品的候选，但没有依据证明它在此项目上必然开发更快。

NestJS 比 Express 更有框架约束，也增加代码量、学习成本与依赖；如实现范围始终很小、维护者熟悉 Express，可用 Express 并明确模块和测试规范。Python Django 同样是成熟可行方案，内置后台和权限是优势，但对本项目前后端分目录的交互系统会引入另一套语言。此推荐不以性能或全球受访比例单独决定。

数据库访问库和 Excel 库在实施设计时按 PostgreSQL 兼容、事务与迁移、维护状态、授权及 Excel 模板支持选型，避免仅凭名称确定。金额使用十进制定点运算，价格计算仅在服务端确定，前端展示结果；提交确认时校验规则和报价版本防止过期确认。

## 4. 部署与风险

应用提供构建好的前端页面，局域网浏览器访问应用电脑 IP 和端口；主机须开机并连通云数据库。采用 Node.js 正式支持的 LTS 版本及跨平台启动方案，并分别验证三个系统；具体版本在实施时根据官方支持状态确定。应用账号和云数据库账号分离、最小授权，密钥不放入仓库。图片保存在应用电脑，需与数据库一起备份和验证恢复。多设备跨网访问暂不纳入。

Node.js LTS 发布策略：https://nodejs.org/en/about/previous-releases
